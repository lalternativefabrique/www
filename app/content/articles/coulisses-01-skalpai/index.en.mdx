## How many tools does it take to put an application online?

For a long time I used Docker Compose to develop locally, Testcontainers to test, GitHub Actions or GitLab CI to automate checks, Tekton to build pipelines, then Kubernetes with Skaffold to bring development closer to production.

On top of that came Argo CD for deployments, Argo CD Image Updater to follow new images, then all the tools observability needs: metrics, logs, traces, alerts and error tracking.

And I am not even naming them all.

Each of these tools is useful. Some are remarkable. The problem was not their quality, but their accumulation.

You had to learn their conventions, maintain their configuration files, handle their upgrades and understand why an application worked on the development machine, failed in CI, then behaved differently again in production.

A growing share of the work no longer consisted of building applications. It consisted of getting the tools that build them to talk to each other.

## Ending the pile-up

The original idea of Skalpai was already to cover the whole journey:

> develop, test, build, publish, deploy and observe.

It was not about adding yet another tool to the chain. It was about replacing that fragmented chain with one coherent system.

The same definition of an application had to serve everywhere. The same environment had to accompany it from the first local run to production. A check that passed during development should not have to be reinvented in a CI file.

Skalpai had to remove as many translations between stages as possible.

## Starting with development

We did not, however, try to build everything at once.

We started with development, because it was the most pragmatic and immediately useful choice.

That is where the loop is shortest. You change an application, run it, look at the result, then start again. Any slowdown in that loop repeats dozens of times a day.

It was also the best place to test the system's foundations. Before trusting Skalpai with a deployment, we had to check that it could already run the same services reliably, reproducibly and in isolation on a development machine.

Starting with development did not shrink the ambition. It was the first step towards deployment.

## One foundation for development and CI

The first concrete step forward was bringing development and continuous integration together.

Code no longer had to cross two entirely different worlds. Services could run in a common environment, with the same dependencies and the same execution rules.

That unity rests on Spaces, Skalpai's execution building block. A Space gathers the services an application needs in an isolated environment. It provides a common frame for development, tests and pipelines.

CI is then no longer a rough reconstruction of the workstation. It becomes the continuation of what has already been run and checked locally.

## Finally using the power of our machines

Macs with Apple Silicon processors have considerable power today. Yet much of that capacity sits idle while developers wait for a remote CI.

Skalpai runs more checks locally and runs several tasks in parallel. Errors show up earlier, before a commit leaves for a server and comes back with a red light.

With this approach, I have considerably increased my ability to test, deploy and observe what I build every day.

The gain does not only come from faster execution. It comes above all from removing part of the round trips and the differences between environments.

## From code to published image

Once continuity between development and CI was in place, Skalpai could move to the next step: producing an artefact ready to deploy.

The system works out which services a change affects, runs their checks, builds the images needed and scans them before publishing them to a registry.

The aim stays the same: not asking the developer to glue every step together with yet another layer of scripts and YAML files.

The pipeline is not a separate world. It extends the work started locally.

## And now, deployment

Deployment was part of the destination from the start. It comes after development and CI because it had to rest on a foundation already proven.

Skalpai now links the stages of the journey:

> development → tests → build → scan → publish → deploy → observe

An application can travel this chain without changing its definition several times or moving from one assembly of tools to another.

This work is still in progress. Skalpai does not claim to replace every feature of Docker, Podman, GitHub Actions, GitLab CI, Tekton, Kubernetes, Skaffold, Argo CD, Datadog, Grafana, New Relic or Sentry.

It offers something else: less need to assemble them all to meet the daily needs of an independent developer or a small team.

## Renting infrastructure without handing over the system

The Fabrique necessarily uses servers, networks and registries provided by hosts. But renting infrastructure does not force us to hand them our whole technical chain.

With Skalpai, we can use their resources while keeping control of the system that develops, checks and deploys our applications.

> We do not own the machines. We own the way our software travels through them.

That distinction is essential for the Fabrique. It lets us change provider more easily, understand what happens at each step and avoid rebuilding our organisation around the constraints of a single platform.

## The Fabrique's foundation

Skalpai was not born because we were missing one more tool.

It was born because we were already using too many.

Its ambition, from the start, has been to bring development, CI and deployment into one system. We started with development because it was the most immediate need and the best place to build solid foundations.

Today, those foundations reach production.

The Fabrique's applications can be developed, tested, published and deployed through a chain we understand and control.

That is why Skalpai became the first episode of this story: before building all the other applications, we had to build the path that would let them exist.
