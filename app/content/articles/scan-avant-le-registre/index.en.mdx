An application does not only contain the code we write.

To run, it also carries a system, libraries and various programs it depends on. The whole thing is bundled into a kind of parcel ready to be installed on a server. In technical terms, that parcel is called a container image.

Before an image can be used, it is placed in a storage space called a registry.

With us, a mandatory step sits between the two:

> Build → check → publish

If the check finds a serious flaw, publication stops.

That is what happened that day.

## First refusal: a useless, vulnerable component

The application in question did a few simple things: fetch a page, extract its text and let you read it or listen to it.

Before publication, the security check found a serious flaw in GStreamer, a component used to decode video content.

No fix was available yet.

The quickest way out would have been to allow publication as an exception. The flaw would have been known and documented, but it would have stayed in.

We preferred to ask another question:

> Why does this application contain a video decoder when it plays no video?

GStreamer came automatically with the browser the application used. It was not needed for it to work.

We removed it.

The application kept working normally. The flaw had not been hidden or accepted: the component that contained it was gone.

## Second refusal: flaws hidden in the dependencies

A new version of the application was built.

The check refused it again.

This time, it had found six serious flaws in libraries the application used indirectly.

We had not added them ourselves. One library used another, which used yet another. That is how a project can carry components nobody knows are there.

The fixes already existed.

An update was enough to replace the vulnerable versions. A few minutes later, a third image was built and checked.

It no longer contained any flaw rated serious or critical.

Publication was allowed.

## Why the check must come first

Security checks are nothing unusual. Many companies scan their applications.

What changes everything is when that scan happens.

If the application is published before it is checked, the vulnerable version becomes available. It may already be installed, copied or running in production when the alert arrives.

Then you have to organise a fix, replace the version and check where it was deployed. A simple update turns into an emergency.

In our case, the vulnerable version never left the machine that built it.

It was not published. It was not installed. No user was exposed to it.

So the fix required no downtime, no rollback and no crisis communication.

## Block only when it matters

A check that constantly blocks publication ends up bypassed or switched off.

Ours therefore follows a simple rule:

- serious and critical flaws block publication;
- lower levels are reported without stopping everything;
- every refusal must give information you can act on;
- the version checked must be exactly the one that will be published.

The check is not there to produce one more report.

It is there to stop a dangerous version from going any further.

## The best incident is the one that never started

That day, no attack took place. No service went down. No user noticed anything.

An application was simply refused twice, fixed, then published cleanly on the third attempt.

Nothing happened.

That was exactly the result we wanted.

> Security is not only measured by the flaws you detect. It is measured above all by the ones that never reached users.
